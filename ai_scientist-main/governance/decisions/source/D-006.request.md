# D-006 最小前端 Read Model 请求

> 状态：`REQUEST_FOR_REVIEW`
>
> 决策上下文：`PROJECT_GOVERNANCE`
>
> 闸门：`GOV_FRONTEND_READ_MODEL`

## 1. 背景

`D-001=A` 至 `D-005=A` 已确认首个 MVP 是离线 SHRGT45 历史 Replay，S04 的 0808/0814 包角色和默认运行边界也已冻结为草案约束。当前仍需决定 API 和前端共同使用的最小 Read Model，避免 UI 直接读取 LangGraph State、历史 Markdown、CSV 或绝对路径。

公共契约已经规定七个领域摘要：`CandidateSnapshot`、`MechanismSnapshot`、`HypothesisSnapshot`、`DataPlan`、`DataDemoSnapshot`、`CounterexampleReviewSnapshot`、`MagnetogramQASnapshot`，以及系统原生的 `ResearchSummary`。本决定只冻结它们如何汇聚为前端查询投影，不改变这些领域摘要的科学含义。

## 2. 共同不变量

- Read Model 是由不可变 Artifact、Ledger 事件、ValidationReport、Finding 和 Decision 投影出的查询视图，不是新的科学事实源；
- 任何版本化对象都用绑定 `id + content_hash + schema_version` 的 ref，前端不能提交裸路径、裸 hash 或自造状态；
- `authorization_status`、`scientific_verdict`、`result_maturity`、`release_scope` 必须分开显示；`PASS` 不得渲染成“科学支持”；
- Run Overview 只放小型摘要和引用。原始 Markdown、CSV、图片和 0808 完整包通过受控详情查询访问；默认 S04 详情仍只展示 0814 运行投影，provenance 详情才展开 0808；
- `55` 行必须同时显示依赖分组和“不是 55 个独立样本”；S05/S06 必须显示为 S04 后的并列分支；
- 读模型变化不回写 Artifact。新的上游内容或 Schema 必须产生新版本和新的 Read Model revision。

## 3. 选项

### A（推荐）：聚合 RunReadModel + 引用式详情

提供一个稳定的 `GET /runs/{run_id}/read-model` 聚合查询，前端首屏只依赖以下字段：

```text
RunReadModel
  run: run_id, task_id, question_ref, case_ref, workflow_version,
       run_mode, run_purpose, execution_status,
       authorization_status, scientific_verdict, result_maturity,
       active_stage_ids[], created_at, started_at, completed_at
  stages[]: stage_id, label, branch_group, execution_status, attempt,
            input_artifact_refs[], output_artifact_refs[],
            validation_report_refs[], finding_refs[], gate_state,
            started_at, completed_at
  domain_snapshots[]: artifact_ref, artifact_type, stage_id,
                      summary_payload, source_asset_refs[], domain_status
  artifacts[]: artifact_ref, artifact_type, origin_mode, authority_mode,
              lifecycle_state, producer, derived_from_refs[], source_asset_refs[]
  findings[]: finding_ref, code, finding_kind, severity, status,
             disposition, replay_policy, required, blocking, related_refs[]
  gates[]: gate_id, gate_type, state, target_refs[], required_action,
          decision_request_ref, decision_record_ref
  lineage_summary: edge_count, verified_count, partial_count,
                   conflict_count, not_checked_count
  report: report_ref, join_policy, join_state, internal_demo_state,
          release_scope
```

详情使用独立端点：`/artifacts/{id}`、`/findings/{id}`、`/lineage?run_id=...`、`/sources/{asset_id}`、`/reports/{id}`。`summary_payload` 只承载七个领域摘要的前端白名单字段，不承载全文。

优点：前端不理解主图拓扑；阶段、闸门、Finding 和报告在同一运行视图中保持一致；未来增加 Live Provider 或新增阶段时，只需增加摘要类型/阶段条目，不改变既有引用关系。代价是需要实现一个聚合投影器和明确的字段白名单。

### B：每个阶段独立 Read Model，前端自行拼装

分别提供 `/stages/{stage_id}` 和七个领域摘要端点，前端按阶段调用并自行计算运行状态、并行分支和最终报告 Join。

优点是后端初期代码少。代价是把工作流语义、Finding 优先级和科学状态传播复制到前端，容易出现“分支已完成但最终报告未 Join”或状态混用；新增 Provider 时前端也要跟着改。

### C：直接暴露 Artifact/历史载荷

API 主要返回原始 Markdown、CSV、图片路径和 LangGraph State，由前端根据文件内容展示。

优点是最初演示最快。代价是绕过公共契约、泄露绝对路径、把 0808/0814 包边界混入 UI 逻辑，并且无法稳定验证权限、哈希和科学主张上限；不符合 MVP 的可扩展性和审计目标。

## 4. 推荐选择

推荐 `A`。它保留前端真正需要的“运行状态、阶段、产物、Finding、闸门、血缘和报告”七类导航，同时把领域摘要和原始载荷隔离在公共契约之后。B 可作为未来分页/缓存策略，C 仅可作为受控的原始来源下载动作，不能作为主 Read Model。

